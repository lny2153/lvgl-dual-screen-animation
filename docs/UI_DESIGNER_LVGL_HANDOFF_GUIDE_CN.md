# UI设计师从 Jitter 动画到 ESP32-S3 / LVGL 固件交付：完整教程

> 适用项目：ESP32-S3 N16R8、左屏 648×200、右屏 240×240、双 TFT、实体按键与 PEDOT 触控膜。  
> 本教程面向不要求会写固件的 UI 设计师。目标不是让设计师取代固件工程师，而是让设计、动画、PC验收和固件接口在进入真机前已经被说清楚。

---

## 0. 先记住最终结论

你的 Jitter、Lottie、MP4 和 GIF 都有价值，但它们不是同一种交付物：

- **Jitter 工程**：设计源文件，负责保存图层、关键帧、曲线和设计意图。
- **MP4**：视觉金标准，固件和设计师用它判断“看起来是否正确”。
- **Lottie JSON**：参数参考，可读取尺寸、时长、颜色、关键帧、路径和缓动；不等于必须在芯片里直接播放。
- **GIF**：当 Lottie 导出失败时的视觉补充，也只应默认作为参考。
- **LVGL 工程**：最终可运行的界面系统，里面是状态、组件、动态数据、事件和动画规则。

真正的工作流是：

```text
Figma / Jitter 设计
        ↓
整理为动画规格与状态规则
        ↓
判断：原生重建 / 混合实现 / 固定播放
        ↓
PC端 LVGL 双屏模拟器
        ↓
设计师逐状态、逐动画验收
        ↓
固件接入屏幕、按键、PEDOT、称重、蓝牙、AI事件
        ↓
真机性能调校和最终验收
```

最重要的原则是：**不要把二十多段动画塞进一个播放器；要把它们拆成一套可以被任意数据、任意用户事件驱动的界面系统。**

## 1. UI设计师需要学习到什么程度

### 1.1 必须真正理解的知识

#### A. 像素与屏幕坐标

你需要理解：

- 左屏运行坐标永远是 `648×200`；右屏永远是 `240×240`。
- PC窗口放大只是为了看清，不能改变 TFT 内部排版坐标。
- 元素位置最终以整数像素落地。
- RGB565 只有 16 位颜色，渐变可能比电脑屏幕更容易出现色阶。
- “透明”并不是屏幕真的透明，而是 LVGL 把前景和背景混色后再输出像素。

你不需要学习 LCD 电气原理，但要能看懂：分辨率、方向、颜色格式、刷新区域。

#### B. LVGL 的对象模型

把 LVGL 理解为一个简化的 Figma 图层树：

```text
screen
├── background
├── data_skeleton
├── primary_visual
├── dialog
└── status_overlay
```

每个对象都有：

- 父级和子级；
- x、y、宽、高；
- 颜色、透明度、字体；
- 显示或隐藏状态；
- 图层顺序；
- 动画中的位置、缩放、旋转等属性。

设计师需要理解“父容器裁切子元素”。滚轮菜单、飞出数值等对象如果要移动到原容器外，应放到整屏动画层，或者让父级允许溢出。

#### C. 局部刷新

局部刷新不限制元素移动。元素从 A 移到 B 时，LVGL 会重画旧位置和新位置，而不是每次都刷新整块屏幕。

设计时要避免：

- 为了让一个数字淡出，却把整个 648×200 页面一起做透明度动画；
- 为了移动一个图标，缩放整块屏幕父容器；
- 用覆盖整屏的半透明层完成一个很小的局部效果。

局部对象越小，越容易接近 60fps。

#### D. 状态、事件和动画不是一回事

三个概念必须分开：

- **状态**：现在界面是什么，例如 `EYES`、`FOOD`、`WARNING`、`CHARGING`。
- **事件**：发生了什么，例如识别成功、重量稳定、蓝牙连接、保存确认。
- **动画**：状态 A 如何过渡到状态 B。

例如：

```text
事件：ADD_ACK
旧状态：FOOD，当前苹果 130g
动画：M006 左右屏添加动画
新状态：EYES，当前值 0，顶部总计增加
```

不能把“播放 M006”当成业务逻辑；M006 只是 `ADD_ACK` 对应的一种视觉过渡。

#### E. 可中断动画

真实用户不会等待动画结束后再操作。你需要为每段动画说明：

- 能否被新事件打断；
- 打断后从当前视觉状态续接，还是立即切换；
- 快速连续点击是累加、忽略，还是改变目标；
- 动画结束是由固定时间决定，还是由业务 ACK 决定；
- 超时、失败和取消时如何退场。

这比“动画多少秒”更重要。

#### F. 时间曲线与空间路径

- 时间曲线决定快慢，例如 `cubic-bezier(0.5, 0, 0, 1)`。
- 空间路径决定沿直线还是弧线移动。
- 缩放、透明度、位置和颜色都可以分别使用缓动，不必匀速。
- 固件动画必须按照毫秒计算，不得每刷新一帧就机械加 1。

如果设备偶尔少画了一帧，按毫秒求值可以保证总时长和左右屏同步不变。

### 1.2 只需要听懂、不必深入的知识

你只需知道它们会影响结果：

- ESP-IDF 是 ESP32 的官方开发框架。
- CMake/Ninja 负责编译工程。
- FreeRTOS 让称重、蓝牙、AI、屏幕等任务同时运行。
- SPI/DMA 负责把像素快速送到 TFT。
- PSRAM 用于较大的运行时数据；Flash 保存程序、字体、图片和模型。
- `lv_display` 是 LVGL 对一块屏幕的抽象；`flush callback` 把局部像素交给真实屏幕驱动。

### 1.3 暂时完全不需要学习的知识

- C 指针和内存管理的全部细节；
- LCD 控制器寄存器；
- FreeRTOS 调度算法；
- 链接脚本、启动代码、Bootloader；
- SPI 波形和 PCB 走线；
- 从零编写屏幕或称重芯片驱动。

这些属于固件职责。设计师只需知道它们会形成哪些约束，并要求固件给出测量结果。

## 2. 动画资源应该怎样分类

### 2.1 A类：必须使用 LVGL 原生、参数化重建

符合以下任意一点就属于 A 类：

- 包含动态重量、营养、单位、食材名称、SOC、电量等数据；
- 用户可以连续按键、滑动或提前退出；
- 动画要等待称重、蓝牙、APP、AI或保存 ACK；
- 同一个效果需要套用不同颜色、数值或食材；
- 需要与真实业务状态严格同步。

例如：实时称重、添加、去皮、营养切换、单位滚轮、类别覆盖、充电。

实现方式：

- `lv_label` 显示文字和数值；
- `lv_arc` 显示圆环；
- `lv_obj` 显示容器、色块和遮罩；
- `lv_image` 显示食材和复杂静态图形；
- `lv_anim` 或统一毫秒时间轴改变位置、缩放、透明度和角度。

### 2.2 B类：混合实现

结构和数据用 LVGL，难以重画的局部视觉使用图片或少量序列帧。

例如：

- 眼睛的复杂渐变外观使用透明 PNG；眼球、眼皮位置用 LVGL 控制；
- 右屏渐变圆环用多段 `lv_arc`，加号用两个圆头矩形；
- 成功状态的环、勾和文字用 LVGL，极复杂的小装饰可使用图片；
- GIF 只负责一个固定循环局部，业务页面仍然是原生对象。

这是大多数复杂产品动画最实用的方案。

### 2.3 C类：允许固定播放

只有同时满足以下条件才建议固定播放：

- 每次内容完全相同；
- 不包含动态数据；
- 不受用户和传感器中途打断；
- 播完只进入一个固定结束状态；
- 资源和解码成本可以接受。

典型例子是品牌开机序列。即使如此，固定动画结束后也要切换到原生 LVGL 稳定页面。

### 2.4 为什么不应默认直接播放 Lottie

LVGL 当前有 `lv_lottie`，但它依赖 ThorVG、C++和矢量渲染，并要求为每个动画准备 ARGB8888 画布。画布内存约为：

```text
左屏：648 × 200 × 4 = 518,400 bytes
右屏：240 × 240 × 4 = 230,400 bytes
两块合计：748,800 bytes，约 731 KiB
```

这还没有计算 JSON、ThorVG、LVGL、字体、图片、AI模型和其他任务。ESP32-S3 N16R8 虽有 8MB PSRAM，但直接播放多个复杂 Lottie 会增加解析、栅格化、混色和 RGB565 转换成本。

因此：

- Lottie 首先是“可读取的设计参数”；
- 小尺寸、固定、确认兼容的动画才考虑真机直放；
- 动态业务动画优先原生重建；
- 当前 PC 工程明确关闭了 ThorVG，因此当前模拟器也不是 Lottie 播放器。

### 2.5 MP4 和 GIF 的正确用途

**MP4：**视觉验收金标准。不要默认把 H.264 视频烧进芯片；普通 LVGL 并不负责 H.264 解码。

**GIF：**Lottie 失真或导出失败时的视觉参考；只有小面积、短时、固定循环效果才值得评估直接播放。

**推荐优先级：**

```text
结构与逻辑：设计说明表 > Lottie图层/关键帧
视觉节奏与质感：MP4 > GIF > Lottie预览
实际运行：LVGL原生/混合实现
```

- VS Code；
- Espressif 官方 ESP-IDF 扩展；

正式 ESP-IDF 工程路径建议使用纯英文且无空格，例如：

```text
C:\esp\calorie_scale_fw
```

不要直接把当前包含中文和空格的设计资料目录作为正式 ESP-IDF 工程根目录。设计资源可以保留原位置，固件仓库另建干净路径。

### 3.3 推荐但非必须

- FFmpeg：查询 MP4 帧率、时长，抽取关键帧；
- LVGL 官方图片转换器：把 PNG/SVG 等转换成 RGB565、RGB565A8 或二进制资源；
- LVGL 字体转换工具：只打包产品实际使用的字形；
- Git LFS：MP4、GIF和大图很多时使用；
- 表格工具：维护动画清单与事件表。

### 3.4 现在不建议额外引入的平台

- 不要因为“可以导出代码”就立即再引入一个 UI 生成器；
- 不要同时维护多套 LVGL 主版本；
- 不要为播放 MP4 引入大型视频解码方案；
- 不要为了一个渐变或弧线引入完整矢量引擎。

当前 Figma + Jitter + LVGL PC模拟器已经足够完成设计验收。

## 4. 从 Jitter 动画整理成“固件能实现的规格”

### 4.1 每段动画保留哪些文件

建议固定命名：

```text
M006_添加_左屏_v03.json
M006_添加_左屏_v03.mp4
M006_添加_左屏_v03.gif       # 仅当需要
M006_添加_左屏_v03_notes.md
M006_添加_左屏_v03_keyframes/
```

不要使用“最终版、最终最终版、新最终版”。版本必须是数字。

### 4.2 每段动画必须填写的规格

| 字段 | 必须写清楚的内容 |
|---|---|
| ID/名称 | 唯一编号，例如 M006 |
| 屏幕 | 左、右、双屏 |
| 触发事件 | 按键、重量稳定、识别ACK、保存ACK等 |
| 前置状态 | 动画开始前界面必须是什么 |
| 结束状态 | 动画完成后留下什么 |
| 动态参数 | 重量、营养值、食材、颜色、单位、SOC等 |
| 固定内容 | 不随业务变化的品牌、提示、装饰 |
| 时长 | 总时长和各阶段时长，使用毫秒 |
| 曲线 | 每个属性使用的缓动 |
| 是否循环 | 循环范围和退出事件 |
| 是否可中断 | 哪些事件能打断，打断后怎么续接 |
| 快速重复输入 | 忽略、累计、续接、改目标还是排队 |
| 超时/失败 | 无ACK、蓝牙断开、识别失败时怎么退 |
| 左右屏同步 | 两屏分别做什么，是否允许某屏NO_OP |
| 实现建议 | 原生、混合、固定播放 |
| 视觉基准 | MP4/GIF/Figma节点 |
| 验收点 | 哪几个关键毫秒必须截图比较 |

### 4.3 不要只写“播放动画”

错误描述：

```text
用户点击加号，播放M006。
```

正确描述：

```text
用户短按加号后先产生ADD_REQUEST；业务层确认当前食材有效并返回ADD_ACK。
收到ACK后，以同一个transition_id和t0_ms启动左右屏M006。
动画中显示本次真实增量；完成后清空当前值，顶部总计使用ACK返回的新总计。
重复点击在ACK前不重复提交；如业务拒绝，则不播放成功添加动画。
```

### 4.4 Lottie 有问题时如何补救

如果 Lottie 缺图层、渐变错误或无法播放，至少交付：

1. MP4；
2. GIF（如果透明或循环更容易观察）；
3. 起点、25%、50%、75%、终点截图；
4. 每个关键对象的边界框；
5. 缓动曲线；
6. 图层进出顺序；
7. 动态数据替换规则；
8. 哪一帧只是示例值，不能写死。

如果复杂局部必须使用序列帧，先把它作为参考序列，不要直接决定全部烧入 Flash；由固件评估压缩后再决定。

## 5. 在 LVGL 中搭建框架，而不是搭建动画播放器

### 5.1 第一层：稳定态组件

先做静止时真正可以使用的界面：

- 左屏数据骨架；
- 默认眼睛；
- 食材区域；
- 当前重量和累计重量；
- 当前营养与累计营养；
- 右屏加号、底环和目标进度；
- 警告、成功、充电等独占页面。

先用任意合法数据测试：

- `0g`、`1g`、`999g`、`1999g`；
- 小数和不同单位；
- 不同长度的中文食材名；
- 极小、极大营养值；
- 目标为空、达到、超过。

只有稳定态正确，动画才有正确的起点和终点。

### 5.2 第二层：严格的视觉模式互斥

左屏主视觉只能属于一个模式：

```text
EYES | FOOD | WARNING | STATUS
```

右屏主视觉也只能属于一个模式：

```text
PLUS_ONLY | PLUS_RING | ADD_RING | FINISH_HOLD |
UPLOAD_SPINNER | SAFETY_PULSE | CHARGE_RING | OFF
```

切换时先统一隐藏所有主视觉，再显示目标模式。不要依赖图层覆盖错误对象。

### 5.3 第三层：数据快照

LVGL 不应自己计算营养、判断食材或猜测重量。每次业务事件都带一份一致的数据快照：

```json
{
  "transition_id": 42,
  "event": "ADD_ACK",
  "t0_ms": 128340,
  "snapshot": {
    "food_id": "apple",
    "food_name": "苹果",
    "current_weight_g": 0,
    "total_weight_g": 130,
    "current_nutrient": 0,
    "total_nutrient": 67,
    "nutrient_type": "calories",
    "unit": "g",
    "ble_connected": true
  }
}
```

左右屏必须读取同一个快照，不能各自在不同时间查询业务数据。

### 5.4 第四层：统一转场控制器

每次双屏动画只创建一次：

```text
transition_id
t0_ms
from_state
to_state
snapshot_before
snapshot_after
```

每一帧使用：

```text
elapsed_ms = now_ms - t0_ms
```

左屏和右屏用同一个 `elapsed_ms` 求值。SPI 发送可能相差几毫秒，但动画逻辑不会漂移。

### 5.5 第五层：动态动画函数

不要为每个数值制作一段动画。应把动画写成参数函数：

```text
render_add(elapsed_ms, old_total, increment, new_total, theme)
render_nutrient_switch(elapsed_ms, old_type, new_type, values)
render_unit_switch(elapsed_ms, current_unit, target_unit)
```

贝塞尔曲线只负责把 `0～1` 的时间进度变成平滑进度；位置、缩放、透明度、角度分别使用这个进度计算。

## 6. PC端模拟器应该怎样使用

### 6.1 PC模拟器能确认什么

- 尺寸、间距、字体和对齐；
- 颜色和渐变方向；
- 状态互斥；
- 动画节奏和关键帧；
- 快速点击、打断、超时和失败；
- 动态数据是否会破版；
- 左右屏是否使用相同时间轴；
- LVGL API 本身是否支持目标效果。

### 6.2 PC模拟器不能证明什么

- 真实 TFT 的颜色、亮度、可视角度；
- SPI 实际帧率；
- RGB565 色阶；
- 触控膜噪声和手指压力造成的称重波动；
- 双屏总线竞争；
- AI、Wi-Fi、蓝牙同时运行时的性能；
- 真机休眠和唤醒时序。

因此 PC验收通过是必要条件，但不是最终真机验收。

### 6.3 当前工程的正确使用方式

当前工程目录：

```text
lvgl-dual-screen-ui-rebuild
```

首次准备环境：

```powershell
PowerShell -ExecutionPolicy Bypass -File .\scripts\bootstrap.ps1
```

日常预览直接双击：

```text
启动预览.bat
```

当前画布必须保持：

- 左屏 `648×200`；
- 右屏 `240×240`；
- PC外层窗口尺寸不得参与内部布局计算。

### 6.4 建议增加的设计验收入口

模拟器最终至少应提供这些测试动作：

- 任意输入重量；
- 切换食材和识别置信度；
- 触发每个业务事件；
- 快速连续点击加号和单位键；
- 模拟 ACK 成功、失败和超时；
- 模拟蓝牙连接但 APP 无响应；
- 模拟低电量、极低电量、超重和充电；
- 模拟左右屏刷新延迟；
- 暂停在任意毫秒查看关键帧。

这些是测试工具，不得出现在最终 TFT 稳定态里。

### 6.5 如何进行视觉验收

对每段动画至少检查：

1. 起点；
2. 第一个明显动作；
3. 最大形变；
4. 主视觉交接点；
5. 新状态完全出现；
6. 最终稳定态。

建议把模拟器和 MP4 同时录制，统一到同样尺寸和时长，再做：

- 并排比较；
- 50%透明度叠加；
- 关键帧截图；
- 慢速播放检查突然跳变；
- 原速播放检查节奏。

不要只看某一张截图。动画正确需要同时满足路径、时间、层级和结束状态。

## 7. UI如何与称重、按键、PEDOT、蓝牙和AI对接

### 7.1 推荐的数据流

```text
称重芯片 / PEDOT / 实体按键 / 蓝牙 / AI
                    ↓
            固件业务逻辑层
                    ↓
      统一UI事件 + 一致的数据快照
                    ↓
            UI转场协调器
              ↙          ↘
          左屏LVGL      右屏LVGL
```

传感器和通信任务不能随意直接修改某个 LVGL 标签。它们只发送事件和数据；UI在自己的任务中统一更新。

### 7.2 至少需要定义的输入事件

#### 称重

- `WEIGHT_LIVE`：实时重量，建议10～20Hz更新显示；
- `WEIGHT_STABLE`：稳定重量；
- `WEIGHT_REMOVED`：重量接近零；
- `OVERLOAD_ENTER / OVERLOAD_CLEAR`。

实时重量不应做滚动数字动画，否则显示永远追不上真实传感器。

#### 食材识别

- `RECOGNITION_STARTED`；
- `RECOGNITION_RESULT`；
- `RECOGNITION_FAILED`；
- `CATEGORY_OVERRIDE`。

结果中必须带食材ID、名称、状态、置信度和图片资源ID，不能只传中文字符串。

#### 添加、去皮和结束备餐

- `ADD_REQUEST / ADD_ACK / ADD_REJECTED`；
- `TARE_REQUEST / TARE_ACK / TARE_REJECTED`；
- `SAVE_REQUEST / SAVE_ACK / SAVE_FAILED`。

成功动画只能由 ACK 启动，不能在用户手指动作发生时就宣告成功。

#### 连接与同步

- `BLE_PAIRING`；
- `BLE_CONNECTED`；
- `BLE_DISCONNECTED`；
- `APP_SESSION_READY`；
- `APP_UNRESPONSIVE`；
- `UPLOAD_STARTED / UPLOAD_ACK / UPLOAD_FAILED`。

“蓝牙连接”只说明链路建立，不代表手机 APP 已经准备好接收业务数据。这两个状态必须分开。

#### 电源

- `LOW_BATTERY`；
- `CRITICAL_BATTERY`；
- `CHARGING_STARTED / SOC_CHANGED / CHARGING_FULL`；
- `SLEEP_REQUEST / WAKE / POWER_OFF`。

### 7.3 UI向固件发送的意图

UI或输入层只应发送意图：

- `UI_INTENT_ADD`；
- `UI_INTENT_TARE`；
- `UI_INTENT_FINISH`；
- `UI_INTENT_UNIT_NEXT`；
- `UI_INTENT_CATEGORY_SELECT`。

业务层验证成功后再回 ACK。这样界面不会因为一次误触或通信失败显示错误成功状态。

### 7.4 PEDOT 与去皮的特别规则

PEDOT 不是精准坐标触摸屏，应先由输入层转换成语义事件：

```text
PEDOT_TAP_CATEGORY_1..4
PEDOT_SWIPE_LEFT_CANDIDATE
PEDOT_RELEASED
```

去皮建议流程：

1. 识别到明确的连续左滑，而不是单点变化；
2. 等待手指释放；
3. 忽略释放后的短暂压力波动；
4. 称重层重新判断稳定；
5. 业务层确认允许去皮；
6. 返回 `TARE_ACK`；
7. UI播放去皮成功。

手指按压造成的重量变化不得直接成为新的称重基线。具体距离、时间、稳定窗口需要真机校准，因此固件必须保留参数，而不能写死不可调整常量。

### 7.5 实体单位键的特别规则

- 按键做硬件消抖，但不得为了等动画结束而锁死按键；
- 第一次按键打开菜单；
- 后续按键更新 `target_unit`；
- 快速按键改变目标并保留当前滚动速度；
- 最后一次按键后重置自动关闭计时；
- 菜单关闭后单位和数值必须是同一个快照中的结果。

## 8. 双屏、刷新率和性能预算

### 8.1 先理解最坏情况

RGB565 每像素2字节：

```text
左屏完整一帧：648 × 200 × 2 = 259,200 bytes
右屏完整一帧：240 × 240 × 2 = 115,200 bytes
双屏完整一帧：374,400 bytes
双屏完整60fps：约22.46 MB/s，尚未计算协议开销
```

如果两块屏共享普通单线 SPI，总是全屏刷新，60fps通常不现实。目标应是：

- 动画按60fps时间基设计；
- 固件按真实毫秒采样；
- 局部动画尽量接近60fps；
- 全屏大转场至少稳定30fps；
- 不允许因为掉帧而改变动画总时长。

### 8.2 固件应采用的方向

- `LV_DISPLAY_RENDER_MODE_PARTIAL`；
- 每块屏使用合理大小的局部绘制缓冲；
- DMA异步传输；
- 只在DMA真正结束后通知 LVGL flush 完成；
- 尽量避免全屏透明度和全屏缩放；
- 同一 LVGL tick 更新左右屏对象；
- AI推理不要直接阻塞UI刷新任务；
- 实测每块屏的 flush 时间，而不是只讨论理论帧率。

### 8.3 设计师可以主动降低的负担

- 让变化集中在小区域；
- 固定背景保持不动；
- 用对象移动代替整屏视频；
- 用2～3个渐变节点，而不是数十层透明图；
- 用24～36段短弧模拟渐变圆环，不用几百段；
- 不同时播放多个大GIF/Lottie；
- 警告状态和普通页面严格互斥，避免无意义地同时绘制。

### 8.4 N16R8 需要确认的资源预算

`N16R8`通常表示16MB Flash和8MB PSRAM，但设计师不能把16MB全部当动画空间。必须向固件索取：

- Bootloader和分区表占用；
- 主程序占用；
- AI模型及其工作内存；
- 字体占用；
- 食材图片占用；
- OTA是否需要双应用分区；
- 实际剩余Flash；
- 峰值PSRAM和内部RAM余量。

没有这张预算表之前，不应决定把大量序列帧烧进芯片。

- 先测位置/缩放/透明度；

- AI推理过程中播放重动画；
- 蓝牙上传过程中操作界面；
- APP无响应、断开和重连；

## 14. 最容易踩的坑

1. **把Lottie能打开理解为适合真机直接播放。** 能播放不等于资源和帧率合理。
2. **把MP4中的示例值当固定业务值。** 130g、某个苹果或某个热量都只是示例。
3. **只交动画，不交前置状态和结束状态。** 固件无法知道何时显示什么。
4. **每次点击都从第一帧重播。** 快速交互一定会停顿。
5. **动画结束直接当业务成功。** 成功必须来自ACK。
6. **PC上60fps就认为真机也是60fps。** PC不包含SPI和AI压力。
7. **为了渐变直接导出全屏视频。** 两个LVGL渐变色块通常更简单。
8. **左右屏各自启动定时器。** 长时间后会产生可见错拍。
9. **传感器任务直接改LVGL对象。** 容易线程冲突和视觉状态不一致。
10. **用图片遮住错误图层。** 被遮住的对象仍可能重绘、接收事件或再次露出。
11. **不固定LVGL版本。** 9.5和在线master的API与行为可能不同。
12. **把正式ESP-IDF工程放进带空格或复杂字符的路径。** 构建工具链更容易出现无意义问题。
